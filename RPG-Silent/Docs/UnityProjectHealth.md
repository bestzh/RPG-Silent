## 设计决策与次级优化

- **暂停语义**：GamePauseService 当前只是停用动作输入，世界仍运行。这是已确认行为，未直接判作 bug。作为单机项目，建议明确“暂停冻结世界、传送选择是否冻结”的规则，再统一冷却、AI、物理和 UI 时间源。
- **玩家传送朝向**：Spawner 写 Transform/Rigidbody 朝向，PlayerController 下一帧又使用私有 yaw 写回朝向。后续应提供统一 Teleport/ResetLook 接口，验证出生点朝向与相机一致；这是代码风险，未实际复现。
- **动画命中来源（已修复）**：普攻统一由 AttackState 时间线释放，技能事件与兜底通过独立上下文保证一次释放；详见 H05 修复记录。
- **玩家死亡动画（已修复）**：H07 补齐参数、终态和动作计时清理；三姿态死亡及死亡后菜单/重开已通过 MCP。
- **设置完成度**：小地图 RawImage 的 texture 为空；亮度 ApplyBrightness 尚未改变画面；震屏尚未发现战斗触发。要么完成这些设置的效果，要么先隐藏未完成选项。
- **技能表现**：六个当前技能均即时释放且无 Animation 引用；“霜冻”“贯穿”只是名称，不应默认已有冰冻或多目标穿透。优先完善 2–3 个技能的动作、音效和反馈，再扩数量。
- **代码组织**：保留现有 Domain/Application/服务/FSM 结构；在引入测试时按稳定边界逐步拆程序集。先清理真实重复入口和过期注释，避免一次重命名所有目录或大规模重写。
- **包固定**：Unity MCP manifest 使用 `#main`，lock 文件已有具体 hash。以后更新依赖时记录并固定验证过的版本/提交；本次不升级任何包。
- **资源目录**：第三方示例与美术包不是第一方债务。先根据构建内容报告确认哪些进入包体，再决定移出或拆分；不要为了整洁直接删除资源。

## 后续开发流程与验收门槛

### 阶段 1：基础稳定

目标：解决 H01–H06，并建立 H10 的最小回归集合。

- 按顺序处理命中特效回收、HUD 幂等、全局根/会话生命周期、输入统一、每次攻击上下文、加载失败与并发请求。
- 先记录对应缺陷触发步骤，再做局部修复；不要把战斗、UI、场景切换打包成一次大重构。
- 增加玩家扣血下限、死亡不重复奖励、能量不足不施法等规则测试；对 UI 重开、两个弹体和场景往返增加针对性回归。

通过门槛：命中 100 次后特效不持续增长；HUD 重开 10 次无重复通知；场景往返 3 次无重复全局根；改键连击正常；加载失败能恢复操作。

### 阶段 2：完成一个有反馈的战斗遭遇

依赖阶段 1。目标：处理 H07，形成可理解、可躲避、可击败的敌人。

- 配好一个敌人的完整 Animator 和攻击前摇/命中帧/后摇。
- 明确普攻、施法、翻滚、跳跃和受击之间的允许/打断关系。
- 先精修近战、远程、范围三种代表技能；接受击音效、命中特效、伤害提示及适量震屏。
- 加警戒、脱战和归位，防止敌人无限追踪；复核寻路与刚体配置。

通过门槛：玩家能观察并躲避攻击；受击与死亡可见；击杀奖励只发一次；同次攻击不重复结算，不同攻击不相互吞伤害。

### 阶段 3：打通一个完整副本

依赖阶段 2。目标：处理 H08，优先完成一个副本，而非只增加列表条目。

- 建立副本状态：进入、进行中、成功、失败、结算、退出。
- 先用“清除指定敌人”作完成条件，接通难度与怪物/奖励配置。
- 成功显示结算并返回主场景；死亡显示失败，可重试或返回。
- 出生点、朝向、玩家生命和能量的重置规则明确；退出时清理 DungeonLaunchContext。

通过门槛：从菜单进入副本，胜利或死亡均有明确出口；结算只执行一次；第二次进入没有上一轮敌人、特效或状态残留。

### 阶段 4：成长与存档

依赖已稳定的会话/结算流程。目标：处理 H09，让奖励有持续价值。

- 在实现阶段 3 时提前定义最小存档字段和版本；本阶段落实保存、读取、备份与迁移。
- 经验对应等级与属性增长；明确金币用途和技能解锁/装配规则。
- 保存玩家成长与装备技能槽；临时战斗状态通常不直接照搬为存档。
- 主菜单区分新游戏与继续游戏；复核退出、异常中断和重复结算。

通过门槛：关闭进程后恢复进度；新游戏正确重置；旧版/损坏数据有可理解的恢复路径；不会重复领取结算奖励。

### 阶段 5：任务、物品与内容扩充

依赖稳定的奖励、成长和存档模型。

- 评估 CustomQuest 的实际适配成本，通过适配层调用现有奖励/副本服务；只保留一个任务事实来源。
- 首先完成“接任务 → 击败指定敌人 → 回交 → 获得奖励/物品”这一条任务。
- 增加最小背包和装备流程：拾取、查看、使用/装备、属性变化、保存。
- 再扩第二种敌人、第二个有差异的副本和更多任务，避免同时搭建多套未完成系统。

通过门槛：任务进度重启后仍在，奖励只发一次，物品数量和装备属性一致；新副本拥有不同内容或明确的变体规则。

### 阶段 6：表现、性能和交付

性能记录与构建检查从阶段 1 开始，本阶段完成系统性收尾。

- 补齐小地图、亮度、声音与输入设置，完成实际有效的选项。
- 按实测结果优化场景、粒子、寻路和 UI，不以场景文件大小替代性能结论。
- 固定 Addressables 内容构建、Windows 构建与包外运行检查步骤。
- 验证首次启动、改键/设置恢复、长时间战斗、反复切场景、存档恢复以及完整副本流程。

通过门槛：目标机器达到约定帧率/加载预算；稳定后内存和实例数量不持续增长；Windows 构建可以独立完成主要流程，新增错误被清零或明确记录。

## 每项开发任务统一流程

1. 写清触发条件、预期行为和可观察的验收结果。
